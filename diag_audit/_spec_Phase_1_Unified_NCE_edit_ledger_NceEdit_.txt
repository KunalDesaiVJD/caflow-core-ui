PHASE: Phase 1 — Unified NCE edit-ledger (NceEdit[]) replacing the 6 metadata channels + 3 per-row flags

SUMMARY:
Introduce ONE typed, serialisable edit-ledger `manualEdits: NceEdit[]` on `NCENoteData`, persisted as a new JSONB metadata key `cy_data._manual_edits` (no DB schema change). It mirrors Corporate's `manual_edits[]` (src/lib/notesAutoPopulate.ts:1065-1092) but is a discriminated-union array instead of a dot-path string array, because NCE edits are structural (custom rows, hides, moves, reclass) not just leaf-value overrides. `deserialiseNoteData` gains a backward-compat shim that folds the 6 OLD channels (_custom_rows, _hidden_rows, _label_overrides, _ejected_ledgers, _source_label_overrides, _cy_sources) plus the 3 per-row flags (source:'manual', tbDerived, userMoved) into `manualEdits` on load; `serialiseNoteData` DUAL-WRITES both `_manual_edits` AND all old channels for one release so live `nce_financial_notes` rows keep working in older builds. A new `respectNceManualEdits(auto, existing)` overlay function rebuilds notes purely from TB+COA then overlays the ledger, letting `nceAutoPopulate` drop its aggressive multi-stage stale-purge (lines 988-1105, 2140-2883) in favour of build-then-overlay. Custom rows gain a mandatory `amountPy` carrier so PY stops under-reporting.

NEW TYPES:
  export type NceEditCol = 'lt' | 'st';
  // Discriminated union — ONE typed edit per user action. rowId is the NCECustomRow.id (custom) or NoteRowDef.id (static). col only for Pattern-A LT/ST notes. cy/py are the post-edit absolute values for value/custom kinds.
  export type NceEdit =
  | { kind: 'value';   noteType: string; rowId: string; col?: NceEditCol; cy?: number; py?: number }            // raw cell figure override (handleChange)
  | { kind: 'label';   noteType: string; rowId: string; col?: NceEditCol; ledger?: string; label: string }      // rename custom row / static row / source sub-ledger (ledger set ⇒ source-label scope)
  | { kind: 'hide';    noteType: string; rowId: string; target?: 'static' | 'custom' }                          // soft-delete a static row (or tombstone a custom row)
  | { kind: 'custom';  noteType: string; rowId: string; label: string; section?: string; attachedTo?: string; ejectedSource?: string; tbDerived?: boolean; col?: NceEditCol; cy?: number; py?: number }  // a manually-added or ejected standalone row, PY carried explicitly
  | { kind: 'move';    noteType: string; rowId: string; attachedTo?: string; section?: string }                 // re-parent a row via Move to… (handlePromoteCustomToStatic)
  | { kind: 'reclass'; noteType: string; rowId: string; ledger?: string; fromCol?: NceEditCol; toCol?: NceEditCol; ejectFrom?: string };  // LT↔ST swap, ledger ejection-from-source, or note re-ownership
  export function foldLegacyChannelsToEdits(customRows: NCECustomRow[], hiddenRows: string[], labelOverrides: Record<string,string>, ejectedLedgers: string[], sourceLabelOverrides: Record<string,string>, cy: Record<string,number>, py: Record<string,number>): NceEdit[];
  export function respectNceManualEdits(auto: NCENoteData, existing: NCENoteData): NCENoteData;
  export function addNceEdit(edits: NceEdit[], edit: NceEdit): NceEdit[];   // dedupe by (kind,rowId,col,ledger) — last-write-wins, mirrors markManualEdit
  export function removeNceEdit(edits: NceEdit[], predicate: (e: NceEdit) => boolean): NceEdit[];   // mirrors clearManualEdit
  export function findNceEdit(edits: NceEdit[], kind: NceEdit['kind'], rowId: string, col?: NceEditCol): NceEdit | undefined;
  // private in nceAutoPopulate.ts: function applyNceEdit(note: NCENoteData, edit: NceEdit): void;  and  function projectEditsToLegacyChannels(edits: NceEdit[]): Pick<NCENoteData,'hiddenRows'|'labelOverrides'|'ejectedLedgers'|'sourceLabelOverrides'> & { customRowPatches: ... };

BACK-COMPAT:
Live data in nce_financial_notes today stores edits across 6 cy_data keys (_custom_rows, _hidden_rows, _label_overrides, _cy_sources, _ejected_ledgers, _source_label_overrides — see META_KEYS line 601) plus 3 per-row flags inside _custom_rows entries (source:'manual', tbDerived, userMoved). Compat is two-directional and lossless for one release: (1) READ — deserialiseNoteData prefers an existing rawCy._manual_edits when present and valid; otherwise foldLegacyChannelsToEdits synthesises the ledger from the 6 old channels + 3 flags, so every existing row loads with a correct ledger with zero migration. (2) WRITE — serialiseNoteData DUAL-WRITES: it keeps emitting all 6 old keys (so an older deployed build, or getNCENoteFaceTotal which reads _custom_rows at line 508, and the renderer in NCEDetailedNotes, all keep working byte-identically) AND additionally emits _manual_edits. respectNceManualEdits also re-derives the legacy channels from the ledger (projectEditsToLegacyChannels) so the in-memory NCENoteData still has hiddenRows/labelOverrides/cy_sources populated for downstream consumers that have not yet migrated. No schema migration, no types.ts change (the new key lives inside existing JSONB cy_data). persistNoteLabels (NCEDetailedNotes.tsx:2784) must add _manual_edits to its overlay so label-only saves don't drop the ledger.

RISKS:
  - DUAL-WRITE DRIFT: if a value edit lands ONLY in _manual_edits but not in the numeric cy/py keys (or vice-versa), getNCENoteFaceTotal (reads cy_data numeric keys + _custom_rows) and the export reconciliation (fsReconciliation.ts) could disagree with the ledger. Mitigation: applyNceEdit must write BOTH the numeric cy/py key AND the ledger entry; projectEditsToLegacyChannels must reproduce the exact pre-Phase-1 channel shape. Add an assertion test comparing serialise(deserialise(old)) ≡ old for the 6 channels.
  - REMOVING THE AGGRESSIVE PURGE could re-introduce the very ghosts those blocks were added for (SHREE HARI opposite-side _st ghosts 2491-2533, OM REALTY 5× inflation 2646-2790, MAHARSH stale manual rows 2140-2286). Mitigation: respectNceManualEdits must (a) rebuild the auto layer from scratch every run — so stale auto values can't survive — and (b) only re-apply EXPLICIT ledger edits, never blanket-preserve prev.cy. Keep the build phase's TB-authoritative writes; the ghosts came from preserving manual rows the user never touched, which the ledger no longer does. Validate against the named clients in the comments before removing each block.
  - ORDER SENSITIVITY: edits must apply in a deterministic order (value < custom < move < reclass < hide < label, or insertion order). A move applied before its custom-row creation would no-op. Mitigation: applyNceEdit tolerates missing rows (create-on-demand) and respectNceManualEdits iterates in stored order (append-only ledger, last-write-wins via addNceEdit dedupe).
  - FOLD AMBIGUITY: a custom row that is simultaneously moved+renamed+ejected currently encodes state across source/userMoved/attachedTo/ejectedSource/label on ONE NCECustomRow. foldLegacyChannelsToEdits must emit MULTIPLE edits (custom + move + label + reclass) for such a row without double-counting amounts. Mitigation: amounts go ONLY on the custom edit; move/reclass/label carry no figures.
  - PY UNDER-REPORTING REGRESSION: the spec mandates amountPy on custom edits, but existing _custom_rows in live data may have rows whose PY only lives in py[id] not in sources[].amountPy. foldLegacyChannelsToEdits must read py[id]/py[id+'_lt']/py[id+'_st'] when synthesising the custom edit's py, not assume amountPy is present (NCEMergedSource.amountPy is optional, line 261).
  - NCEDetailedNotes value edits are currently write-protected (scheduleSave no-op, line 2715). If handleChange records a ledger entry in-memory but no persist path fires, the edit is lost on reload. Mitigation: confirm the only persisted figure path is commitMoveGuarded→persistOneNote (total-preserving) — pure figure edits are intentionally not persisted today, so recording them in the ledger is in-memory-only until a guarded action serialises. Document this so reviewers don't expect figure-edit persistence in Phase 1.

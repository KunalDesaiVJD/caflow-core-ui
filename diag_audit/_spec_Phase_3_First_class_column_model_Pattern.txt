PHASE: Phase 3 — First-class column model (Pattern A LT/ST) across computeNoteTotals, getNCENoteFaceTotal, computeDisplayData, and nceRecomputePYFromShell

SUMMARY:
Today Pattern A (LT/ST split) is special-cased everywhere: computeNoteTotals has a fully duplicated Pattern-A branch (nceNoteTotals.ts lines 261-349) parallel to the Pattern-B branch (171-259); getNCENoteFaceTotal picks a column with ad-hoc lt/st branching (nceAutoPopulate.ts 565-577); computeDisplayData writes back with two near-identical loops (nceNotesConfig.ts 856-874); and nceRecomputePYFromShell flat-out REFUSES Pattern A (nceRecomputePYFromShell.ts 151-156, PATTERN_A_NOTES set 86-88), leaving borrowings/provisions/investments/loans_advances PY uncorrectable. This phase introduces a single column abstraction — every note is a list of columns (Pattern B = ['all'], Pattern A = ['lt','st']) — so all four callsites iterate columns uniformly instead of branching on pattern, and fixes nceRecomputePYFromShell to do column-aware PY/CY attribution for Pattern A using the per-source `column` field already persisted in `_custom_rows[].sources[]` and `_cy_sources[]`. All changes are pure-logic refactors with no DB schema change and no new metadata channel; existing cy_data/py_data (_lt/_st suffixed keys, bare legacy keys, `column` on sources) are read and written exactly as before.

DEPENDS ON: Phase 1 (sign convention via fsSignConvention.ts — already landed; recompute and aggregation assume signed amounts are produced upstream), Phase 2 (the manual-edits dot-path ledger / metadata-channel work) does not block this phase's aggregation refactor, but if Phase 2 changes how customRows/sources are read, nceRecomputePYFromShell.buildRowOwnership and computeNoteTotals' source-gating must consume the same canonical reader. Sequence Phase 3 AFTER Phase 2 if Phase 2 alters the _custom_rows/_cy_sources read path; otherwise independent.
